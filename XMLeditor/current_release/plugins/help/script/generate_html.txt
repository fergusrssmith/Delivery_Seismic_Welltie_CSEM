other_html/introduction.html
Introduction to the XML Editor Script Plugin
The Script Plugin to the XML Editor allows for the generation of scripts which run various Seismic Unix commands.  A flow is constructed in the normal fashion of XML tree construction, with the exception that clicking on the parameters or parameter nodes allows you to edit them directly.  </p><p>Command Line Options</p><p>Command Line Options</p><p>-r: Launch Script Editor in restricted mode</p><p>plugin-hs="helpset_name": Load a helpset from file or classpath location "helpset_name"</p><p>The Script Plugin (run by adding the command line argument plugin=script.ScriptPlugin) creates one new menu to the menu bar at the top and modifies how things are edited, and if you include a -r command line option, restricts what can be edited.</p><p>First I'll explain editing.  The nodes called parameters and parameter have special edit modes where a dialog opens up with a table listing either the one parameter to edit if you chose to edit a parameter, or all parameters if you chose to edit the parameters node.  Simply click in the boxes you wish to edit, and then choose "Accept" when you're done.  If -r was entered as a command line option, only parameters and parameter nodes will be editable, and nothing will be cuttable, copyable, insertable, or pasteable.  In this mode you can only change the values of the parameters.</p><p>For those editing without -r, you will build or modify a chain of commands interspersed with scatter and gather nodes.  The nodes have icons designed to help you monitor the flow of the job, but until you try to create a script no real error checking is done that way.  But it should be clear following the arrows if some appear to be unhooked.  A scatter and a gather node follow the same restrictions as stand-alone commands:  they must occur after the end of a pipe or another stand-alone command, and they must be followed by a stand-alone command or the start of a pipe.</p><p>Once you've finished editing, it's time to generate or run the script.  Under the bsub scripts menu, you have choices "Show script", "Generate script", and "Execute script".  This do precisely what the sound like.  "Show script" displays the top-level script that would be generated by "Generate script" but with a generic name.  "Generate Script" pops up a dialog asking you what directory to place the scripts in and to provide a base name for the scripts.  The major script to run will be baseName.sh or baseName_bsub.sh for the multi-processor bsub version.  "Exectute Script" first behaves like "Generate Script", then runs the generated script in the current directory.  "Execute Script" also gives you options on how to run the script, like forcing a linear, one-processor run.

other_html/include.html
Including Parameters From Other Files
Above the "parameters" node that every file starts with the user can insert an unlimited number of "include" nodes.  The way that these nodes work is to parse in whatever file is passed in as an argument (which may be specified relatively or absolutley) as another script XML file.  It's parameters are then added to the pool of parameters for the script XML file with the include node, as are the parameters of any includes in the included XML file.  In other words this allows for an arbitrary amount of recursion, so be sure not to include the file itself in an include block.  Any commands in an included file are ignored.

other_html/edit_parameters.html
Editing Parameters with the Script Plugin
The XML tree nodes called "parameter" and "parameters" are edited specially in the XML Editor with the Script Plugin.  It displays a table containing two colums: on the left, names of parameters, and on the right, the values for those parameters.  In restricted mode, only the values are editable.  Note to users in non-restricted mode that to add more parameters you cannot do it from the table but must "Insert ...".

The "View Script..." option in the "Scripts" menu allows users to view a script file much like viewing the XML text for a tree.  This option brings up an "Open File" dialog and then the user selects a file to open.

scriptsmenu/generate_script.html
Generating Script Files
Either the "Generate Script..." option in the "Scripts" menu or the Generate Script button <img src="../../../../icons/generate.jpg"> launch a dialog in which the user sets up how to genereate a group of scripts.  By default linear versions and parallel versions are generated.  The user specifies the directory path where they want the scripts and finally the base name for the scripts.  "base_name".sh runs the linear job and "base_name".bsub.sh runs the parallel (lsf) version.

scriptsmenu/execute_script.html
Generating and Executing Script Files
Either the "Execute Script..." option in the "Scripts" menu or the Execute Script button <img src="../../../../icons/execute.jpg"> launch a dialog in which the user sets up how to generate and then execute a group of scripts.  See help on "Generating Script Files" for details on generation.  After the generation options are set up the user can specify execution operations and then launch it by clicking the "Execute" button.  Then the output of the job is shown in a new window.

commands/scatter.html
Scatter Nodes
These nodes specify how and where to split up a job into multiple parts.  A scatter node specifies a target limit on the number of threads/jobs generated by the scatter, and one or more scatter parameters.  More specifically, the max_number_threads parameter specifies an unlimited number of threads when it equals -1, and specifies the factor by which the current limit will be multiplied otherwise.  (If there are no scatters already, the current limit is 1.)  Scatter parameters must have a name and either a range or the name of a file from which to gather selected values.  The range specifies minimum value, maximum value, and increment, as well as the minimum number of of values to use per thread.  This last value, min_number_per_thread, should be set to -1 to force precisely one value per thread, which is the only legal thing to do unless it is a ranged parameter (such as would be used for bhpread's keylist).  The name of the parameter indicates where to place the values over which the scatter runs.  For example, if the parameter's name is alpha, wherever ${alpha} is encountered then there it will put in the appropriate scatter value.  Note that if the scatter parameter is not found inside the scatter block it will still split and will only accomplish redundant work.  Inside each scatter block there is a special parameter created called indexN where N is the integer reflecting the depth of scatters.  That is, inside two scatters, there is index1 and index2.  index1 refers to the index of the current script with respect to the first scatter, and index2 with respect to the second scatter.  Thus, index1*maximum_value_of_index2 + index2 == the current script index.  It must occur in the flow in the same sort of place a solo command would, specifically not at the beginning, middle, or end of a pipe.

commands/gather.html
Gather Nodes
These nodes really have no functionality other than to close the corresponding scatter.  It reduces the number of threads back to the amount before the corresponding scatter.  It must occur in the flow in the same sort of place a solo command would, specifically not at the beginning, middle, or end of a pipe.
